一、项目背景与核心目标

项目定位

个人项目：AI 驱动的监理标书辅助制作工具。当前主要聚焦于商务标制作（招标文件解析 → 商务标生成 → 标书检查），技术标属第二期。

核心底线：不废标

所有设计围绕三条原则展开：不静默报错、人工兜底确认、状态机显式管理。任何异常都必须暴露，不允许程序自己"默默处理"掉。

业务场景

步骤业务操作程序能力
1上传招标文件（Word/PDF/扫描件）MinerU OCR → 结构化解析 → 解析清单
2人工确认解析结果PARSE_CONFIRMED 门禁，阻断未确认进入下一步
3从素材库提取投标信息FTS5 BM25 检索 + 多轮循环收敛
4匹配模板，生成投标文件docxtpl 渲染 + 规则库检查，不调用 LLM
5导出 PDF 标书PyMuPDF 合并 + 书签

参考项目

GitHub OpenBidKit_Yibiao（易标）。本项目在其基础上增强：商务标自动制作、企业—项目两级数据隔离、人工兜底状态机。

二、学习方法论：从需求到代码的完整链路

本项目的开发过程严格遵循了一套规则驱动的方法论，核心是先落盘再编码。以下是从需求到代码的完整链路：

2.1 需求阶段：spec.md 驱动

原则：所有需求必须写进 spec.md，未经落盘的需求视为未确认，不予实现。
  • spec.md 是单一事实来源（Single Source of Truth），包含：目标、功能需求（FR）、非功能需求（NFR）、约束、假设、验收标准（AC）。
  • 每个需求都标注了优先级（P0/P1/P2）和所属阶段（Phase 1.0 / 1.1 / 1.2）。
  • 需求变更走变更协议：记录变更 → 评估影响 → 用户确认 → 同步更新 spec.md → 记入 CHANGELOG-spec.md → 恢复编码。

2.2 规划阶段：checklist.md + tasks.md 双轨

文档作用使用者
checklist.md每个阶段的检查项，完成即勾选；是"能不能进入下一阶段"的硬门禁用户 + AI 共同维护
tasks.md具体的编码任务，每个 Task 对应一个 PR，完成度明确（待开始 / 编码中 / 已完成）AI 执行，用户审查

2.3 编码阶段：PR 门禁

Step 1
本地全绿
pytest + vitest + ruff + mypy + eslint + tsc + prettier，全部通过才能推送
Step 2
创建 PR
PR 描述中引用 spec.md 中的 AC 条目，说明覆盖了哪些验收标准
Step 3
CI 自动检查
GitHub Actions 跑 Lint → Unit → Integration → E2E → Golden Sample 五层测试
Step 4
用户审查合并
用户 review PR，确认 AC 覆盖后再合并到 main

2.4 代码审查：8 方向并行专项

在发现 9 Critical + 20 Major 缺陷时，采用了 8 个并行子代理同时进行代码审查，每个代理专注一个方向：

方向审查重点
数据安全与隔离企业/项目 ID 是否在所有查询中统一注入过滤
状态机与持久化状态转换是否完整，异常时状态是否可恢复
路径与文件安全路径穿越防护，文件写入原子性
外部依赖正确性包依赖是否声明，API 版本兼容性
错误处理是否静默吞异常，错误信息是否足够定位
前端类型安全TypeScript 类型覆盖，zustand store 一致性
性能与并发异步操作是否正确，资源释放是否完整
测试覆盖核心链路是否有对应的集成测试

2.5 缺陷修复：按业务后果排序，逐条推进

方法论：将 9 Critical + 20 Major 按业务后果从重到轻排序 → 逐条修复 → 报告改动 → 停下等用户确认 → commit → 下一条。绝不自行决定修复顺序，绝不批量处理多条后一起汇报。

三、技术栈与核心原理

3.1 整体架构

┌─────────────────────────────────────────────┐
│  Electron (前端进程)                          │
│  React 18 + Ant Design + Zustand            │
│  - UI 渲染、用户交互、路由                    │
│  - IPC 调用 sidecar                         │
│  - SSE 接收进度流                            │
└──────────────┬──────────────────────────────┘
               │ IPC (sidecar:call / sidecar:stream)
               ▼
┌─────────────────────────────────────────────┐
│  Sidecar (Python FastAPI，子进程)             │
│  - 数据持久化：SQLite + SQLAlchemy ORM       │
│  - 文档解析：MinerU（OCR + 结构化提取）       │
│  - 文档渲染：docxtpl（模板填充）              │
│  - PDF 处理：PyMuPDF（合并 + 书签）           │
│  - 搜索索引：FTS5（SQLite 全文搜索）          │
│  - 异步调度：APScheduler（定时清理）          │
└─────────────────────────────────────────────┘

3.2 各技术选型与原理

技术选型理由核心原理
Electron 跨平台桌面应用，内置 Chromium，可访问系统 API（文件对话框、路径） 主进程（Node.js）负责系统交互，渲染进程（React）负责 UI；两者通过 IPC 通信
React 18 + TypeScript 组件化 UI，类型安全；用户熟悉且维护成本低 Zustand 管理全局状态（当前企业/项目），react-router-dom 管理路由
FastAPI Python 最快 Web 框架，原生 async/await，自带 OpenAPI 文档 Sidecar 以 HTTP Server 运行（本地 127.0.0.1），Electron 通过 IPC 转发请求
SQLite 零配置单机数据库，单文件存储，适合个人工具 每个企业有独立数据库文件（enterprises/{id}/bidcraft.db），天然隔离；Alembic 做迁移
MinerU 开源 OCR + 文档解析引擎，支持 PDF/Word/扫描件，输出结构化 Markdown 独立 .venv-mineru（torch/paddle 很大，与主 venv 隔离）；仅本机开发使用，不进 CI
docxtpl 基于 Jinja2 模板引擎的 Word 生成库，保留模板格式 模板是 .docx 文件，内含变量占位符（{{ var }}）；渲染时填充数据，生成新 docx
PyMuPDF (fitz) 高性能 PDF 处理库，支持合并、书签、压缩 docxtpl 生成 .docx → LibreOffice 转 PDF → PyMuPDF 合并多章节 PDF + 添加书签
FTS5（SQLite 扩展） SQLite 内置全文搜索引擎，无需额外依赖 素材 OCR 文本写入 FTS5 索引；提取时做 BM25 排序检索；异步增量更新
DPAPI（Windows 凭据管理器） Windows 原生加密，API Key 不存明文 使用 cryptography 库的 Fernet + DPAPI 加密存储模型密钥

3.3 核心设计模式

模式 1：企业—项目两级数据隔离

所有数据库查询必须携带 enterprise_id 和 project_id 过滤条件，仓储层统一注入，不得绕过。这是地基级约束，违反即灾难性数据泄漏。

模式 2：状态机显式管理

标书制作的每一步（上传 → 解析 → 确认 → 提取 → 匹配 → 渲染 → 导出）均由状态机管理。状态转换全程留痕（audit log）。非法转换被拒绝，不静默。

模式 3：原子写入

所有文件生成操作：先写 .tmp 临时文件 → 完成后 rename → 替换正式文件。异常中断不产生半截损坏文件。

模式 4：侧车（Sidecar）进程隔离

Python 服务作为 Electron 的子进程运行（不独立监听网络），通过 IPC 通信。好处：（1）端口无冲突；（2）Electron 退出时 sidecar 自动终止；（3）随机端口 + 本地令牌鉴权。

八、过程中的关键教训

8.1 最严重的 3 个坑

🔴 坑 1：PyMuPDF 漏声明依赖 → CI 红

现象：本地 280 个测试全绿，CI 上 6 个 PDF 测试失败。排查半天才发现是 pyproject.toml 没声明 pymupdf 依赖，CI runner 严格按 pyproject.toml 安装，装不上。

根因：本机已经手动 pip install pymupdf，所以本地能用；CI 环境没有这个隐式依赖。

沉淀为规则 12：pyproject.toml 必须显式声明所有 import 的包；本机全绿 ≠ CI 全绿。

🔴 坑 2：归档成功后 unlink 用户源文件

现象：用户上传素材后，素材库归档成功，但用户原始文件被删除（original_path.unlink()）。

根因：代码注释写的是"清理收件箱"，但实际删除的是用户上传的原始文件，而非收件箱副本。用户没有任何恢复途径。

沉淀为规则 7（已有）：素材库/模板库是基座，有任何不妥当必须实时披露，不得静默。

🟠 坑 3：electron 路由白名单正则不含下划线

现象：多个真实窗口（materials/from_path、templates/from_path、parse/format/add_path）全部"非法路由"报错，不可用。

根因：路由白名单正则 /^\/api\/v1\/[a-z0-9]+(?:\/[a-z0-9]+)*$/ 不含下划线字符 _，而真实路由大量使用下划线。

教训：安全限制必须与实际业务路径对齐，否则会把正常功能也拦截掉。

8.2 架构层面的关键决策

决策当时为什么这样选后续影响
SQLite 而非 PostgreSQL个人使用，零配置，单文件数据库便于备份和分发FTS5 搜索能力受限（需 SQLite ≥ 3.38），但满足当前规模
Sidecar 作为子进程而非独立服务避免端口冲突，避免用户需要单独启动 Python 服务Electron 退出时 sidecar 自动终止，简化了生命周期管理
MinerU 独立 venvtorch/paddle 数 GB，与主 venv 隔离，避免依赖冲突不进 CI，本机开发专属，体积较大但干净
真实样本存 samples-local/（gitignored）投标文件含敏感信息，不推送到公开仓库CI 上 golden sample 测试无法跑（samples/ 目录为空），属于已知预存问题
docxtpl 而非纯代码生成 Word模板是用户提供的，保留排版；纯代码生成难以匹配用户模板格式需要用户维护 .docx 模板文件，但有格式保障

8.3 已沉淀为项目规则的经验

  • 规则 12（依赖完整性）：pyproject.toml 显式声明，禁止依赖本机隐式安装
  • 规则 13（异常不静默）：禁止 except: pass / except: return False，必须记录日志或暴露错误详情
  • 规则 14（缺陷修复流程）：按业务后果排序 → 逐条修复 → 报告 → 等确认 → 独立 commit → 下一条
