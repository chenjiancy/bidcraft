## 借鉴点汇总表（按优先级排列）

### 优先级说明
- **高**：直接关系"不废标、不静默"底线，或显著影响长任务可靠性，建议在对应阶段首批落地。
- **中**：提升工程质量和用户体验，建议在对应阶段纳入。
- **低**：成本优化或增量改进，可视情况择机落地。

### BP-1 长任务 Checkpoint 与断点续跑

| 字段 | 内容 |
|---|---|
| 优先级 | 高 |
| 适用阶段 | 通用（Phase 1.1 解析 + Phase 1.2 商务标） |
| 关联 spec | NFR-5 可靠性与可恢复性、EM-5 标书生成状态机 |

**易标做法**：
每个解析项独立 checkpoint 落盘（状态：idle/running/success/error + 内容），任务中断后再次启动只跑未成功项；支持选中若干项单独重新解析、整份强制重跑。正文生成 Agent 同样持久化任务与会话，失败小节可单独重试，不阻断其他小节。

**借鉴理由**：
bidcraft 的解析（Phase 1.1）含 8 关键项 + 多个可选项，商务标生成（Phase 1.2）含逐章渲染多文件，均为长任务。若崩溃/中断后从头重跑，成本高、体验差，且可能因网络波动导致云端模型调用失败需重试。NFR-5 已要求"中断恢复"，EM-5 状态机已要求"断点恢复"，checkpoint 是其工程落地手段。

**对 bidcraft 的增益**：
- 解析阶段：18 项中某项 LLM 调用失败，重启后只重跑该项，其余结果保留。
- 商务标阶段：逐章渲染时第 5 章失败，重启后从第 5 章续跑，前 4 章不重做。
- 单项重试：用户可对某项解析结果不满意时单独重解析，不影响其他项。

**具体实例**：
解析阶段开启双通道模式，链路 2（LLM 独立抽取）跑到第 12 项"商务评分要求"时网络超时。checkpoint 记录第 12 项状态为 error，其余 17 项为 success。重启后系统检测到第 12 项未成功，只重跑该项，成功后整体标记完成。

### BP-2 导出占位 + 警告清单（不静默）

| 字段 | 内容 |
|---|---|
| 优先级 | 高 |
| 适用阶段 | Phase 1.2 商务标（渲染输出阶段） |
| 关联 spec | FR-3 第 5 点核心原则（不静默）、FR-6 标书检查 |

**易标做法**：
导出阶段对未生成/失败的节以占位文本标记，并生成警告清单列出所有问题项，不静默跳过。用户可在导出后据此逐项处理。

**借鉴理由**：
bidcraft 的"不静默"原则（FR-3 第 5 点）要求任何不一致、缺失都必须披露。商务标生成时可能出现：占位未填（素材缺失）、图片缺失、差异未确认等情况。若直接跳过，用户不知情，可能导致废标。导出时生成警告清单，是"人工兜底"的最后一道信息披露。

**对 bidcraft 的增益**：
- 符合"不废标、不静默"底线。
- 人工兜底有据可依，导出的 Word 中问题位置有占位标记，检查清单有完整列表。
- 为后续标书检查（FR-6）提供输入。

**具体实例**：
商务标生成后，"投标函"章节中 `{{img_营业执照}}` 占位因素材库未找到对应图片而未填充。导出的 Word 中该位置插入醒目占位文本"【图片缺失：营业执照】"，同时生成警告清单："第 1 章 投标函 - 营业执照图片缺失，请补充素材后重新渲染该章"。用户据此补充素材、单独重渲染该章。

### BP-3 Schema 硬校验与阶段交接门禁

| 字段 | 内容 |
|---|---|
| 优先级 | 高 |
| 适用阶段 | Phase 1.1 解析（score_table.json）+ Phase 1.2 商务标 |
| 关联 spec | FR-2 第 4 点（score_table.json）、NFR-6 数据完整性、EM-5 状态机 |

**易标做法**：
每个产物文件预置 JSON Schema，由 Ajv 编译校验；写入失败即进入修复循环，通过后才允许阶段交接；空文件与占位文件均不算产物，必须实质性内容。

**借鉴理由**：
bidcraft 的 `score_table.json` 是核心对象（FR-2 第 4 点：一处产出、三处复用——素材提取清单、商务标检查清单、AI 评标打分表）。若结构错误，下游消费时崩溃或产生错误结果。NFR-6 已要求"所有清单文件支持结构校验；文件损坏时明确报错，绝不静默忽略"。Schema 校验是这一要求的直接工程手段。

**对 bidcraft 的增益**：
- 数据完整性：`score_table.json`、解析清单、素材提取清单等核心产物结构有硬约束。
- 阶段交接门禁：Schema 校验通过才允许从解析进入商务标，防止错误数据流入下游。
- 错误早发现：结构错误在产出时即报错，而非下游消费时才暴露。

**具体实例**：
解析阶段产出 `score_table.json`，用 JSON Schema 校验结构："评分大类（数组）→ 评分项（数组）→ 分值（number）→ 所需证明材料（数组）→ 门槛条件（object，含日期/金额/数量）"。若 LLM 返回的 JSON 缺少"门槛条件"字段，校验失败，标红要求人工修正，不进入商务标制作阶段。

### BP-4 确定性与语义判断分工

| 字段 | 内容 |
|---|---|
| 优先级 | 高 |
| 适用阶段 | 通用（Phase 1.1 解析 + Phase 1.2 商务标） |
| 关联 spec | FR-2 第 3 点（规则库前置）、EM-3 规则库前置、FR-3 第 4 点（确定性填充） |

**易标做法**：
宿主程序先做全部机械检查（叶子数量、最大层级、单子节点、叶子模式合法性、评分映射覆盖情况），把结果作为上下文直接交给 Agent，明确要求其"直接采用、不要重新统计"；Agent 只负责评分语义覆盖、近义重复与专业合理性。确定性与语义判断边界清晰。

**借鉴理由**：
bidcraft 的解析（FR-2 第 3 点）已采用"规则库前置（确定性）+ LLM 语义判断"分工。商务标生成（FR-3 第 4 点）虽为确定性填充不调 LLM，但模板比对（FR-5 第 6 点）和标书检查阶段同样需要"机械检查 vs 语义判断"分工。明确分工能保证确定性部分可重复、可单元测试，语义部分可控、可追溯。

**对 bidcraft 的增益**：
- 确定性部分（规则库）：可单元测试、可重复、零 LLM 成本。
- 语义部分（LLM）：仅在规则覆盖不到时启用，成本可控。
- 错误可定位：机械检查失败定位到具体规则，语义判断失败定位到具体 LLM 调用。

**具体实例**：
商务标模板比对时，规则库先做机械检查——占位符数量是否匹配、图片尺寸是否合规、表格结构是否一致；全部通过后，若开启 LLM 校验模式，LLM 仅做语义判断——"模板内容是否实质性响应了评分点"、"是否存在近义重复"。机械检查失败直接标红，不进入 LLM 判断，节省成本。

### BP-5 渲染计划（Render Plan）

| 字段 | 内容 |
|---|---|
| 优先级 | 中 |
| 适用阶段 | Phase 1.2 商务标（docxtpl 渲染前） |
| 关联 spec | FR-3 第 4 点（标书制作填充逻辑）、EM-5 状态机 |

**易标做法**：
正文编排对每个叶子节点生成结构化 content_plan（目标字数、表格需求、配图候选标记、可引用知识库条目、来自原方案的素材），编排结果经保存后作为正文 Agent 的执行清单。

**借鉴理由**：
bidcraft 商务标生成（FR-3 第 4 点）是确定性填充（docxtpl + 素材插入），但直接渲染可能导致：占位与素材映射错误、差异项未确认就渲染、图片缺失发现太晚。借鉴"渲染计划"思路：先为每个章节生成结构化填充计划（哪些 A 类占位、哪些 B 类占位、对应素材、差异项），用户确认后再执行渲染。

**对 bidcraft 的增益**：
- 渲染前可预览：用户在渲染前看到每章的填充计划，确认无误再执行。
- 渲染失败可定位：失败时定位到具体计划项（哪个占位、哪个素材）。
- 与 BP-2（警告清单）配合：渲染计划中标记的缺失项，在渲染后进入警告清单。

**具体实例**：
商务标生成前，为"投标函"章节生成渲染计划：
- A 类填充项：企业名称（来源：企业信息）→ `{{企业名称}}`；项目编号（来源：解析清单）→ `{{项目编号}}`
- B 类填充项：营业执照图片（来源：素材库 `营业执照.png`）→ `{{img_营业执照}}`
- 差异项：模板 vs 解析差异 2 处（已确认）
用户确认计划后，执行 docxtpl 渲染。若"营业执照.png"在素材库不存在，计划中标红，用户补充后再渲染。

### BP-6 图片闭环管理

| 字段 | 内容 |
|---|---|
| 优先级 | 中 |
| 适用阶段 | Phase 1.2 商务标（渲染与输出） |
| 关联 spec | FR-3 第 4 点（图片占位）、FR-5 第 5 点（图片占位与尺寸约束）、FR-3 第 5 点（表格图片不跨页） |

**易标做法**：
图片处理从"标记 image_needed → 生成/匹配 → 回填 → 校验尺寸/位置"形成闭环，失败项单独标记不静默。

**借鉴理由**：
bidcraft 商务标有大量图片素材（FR-3 第 4 点"素材基本都是图片"）。需保证全链路：模板图片占位 → 素材库匹配 → 插入 → 按模板尺寸约束等比缩放 → 校验不跨页 → 缺失有披露。当前 FR-3/FR-5 已有相关要求，但需在工程上形成闭环，避免某一环节断裂导致图片丢失或排版错乱。

**对 bidcraft 的增益**：
- 图片不丢失：从占位到插入全链路追踪。
- 尺寸合规：按 FR-5 第 5 点尺寸约束等比缩放（contain），不变形不裁剪。
- 不跨页：校验图片插入后是否跨页，跨页则缩放或换页处理。
- 缺失有披露：图片缺失时进入 BP-2 警告清单。

**具体实例**：
模板中 `{{img_营业执照}}` 占位 → 渲染计划标记需要"营业执照.png" → 从素材库匹配到该文件 → 读取 FR-5 template.json 中的尺寸约束（最大宽度 5cm、最大高度 3cm）→ 等比缩放原图 → 插入 docx → 校验是否跨页（若跨页，缩小至单页内）→ 渲染成功。若素材库无此文件，标记缺失，占位插入"【图片缺失：营业执照】"，进入警告清单。

### BP-7 一致性审计

| 字段 | 内容 |
|---|---|
| 优先级 | 中 |
| 适用阶段 | Phase 1.2 商务标（渲染后、标书检查前置） |
| 关联 spec | FR-2 术语识别、FR-3 第 5 点（不静默）、EM-3 规则库前置 |

**易标做法**：
正文生成 Agent 内置"一致性审计"工具，检查全文术语统一、数据一致、前后引用正确，不一致项列出供修正。

**借鉴理由**：
bidcraft 商务标虽不调 LLM 生成内容，但需保证：术语一致性（FR-2 术语识别——投标人/供应商体系不混用）、企业/项目信息一致性（企业名称、委托代理人前后统一）、日期/编号一致性。这些可用规则库做确定性审计，无需 LLM。审计结果纳入标书检查清单，符合"不静默"原则。

**对 bidcraft 的增益**：
- 避免术语混用（投标人/供应商/响应人）导致废标。
- 避免企业名称、委托代理人前后不一致。
- 为标书检查（FR-6）提供前置输入，部分检查项在生成阶段即可发现。

**具体实例**：
商务标生成后，规则库扫描全文：检查"投标人"与"供应商"是否混用（依据 FR-2 术语识别判定的文件类型）；检查企业名称是否与解析清单一致；检查委托代理人是否前后统一；检查项目编号是否一致。发现"投标函"中写"供应商"而"投标文件格式"中写"投标人"，标红列入检查清单，提示用户修正。

### BP-8 FTS5 全文检索

| 字段 | 内容 |
|---|---|
| 优先级 | 中 |
| 适用阶段 | Phase 1.2 商务标（素材库查询） |
| 关联 spec | FR-4 第 8 点（素材库查询） |

**易标做法**：
知识库用 SQLite FTS5 全文检索，支持关键词高亮、相似度排序。

**借鉴理由**：
bidcraft 素材库查询（FR-4 第 8 点）要求"多条件组合 + 模糊匹配，基于规范化命名查询，按相似度排序"。FTS5 是 SQLite 原生全文检索扩展，与现有 SQLite 技术栈一致，无需额外依赖，查询性能优于 LIKE 模糊查询。

**对 bidcraft 的增益**：
- 查询性能：FTS5 倒排索引远优于 LIKE '%keyword%'。
- 模糊匹配：支持前缀匹配、短语匹配、布尔组合查询。
- 相似度排序：BM25 排序，与 FR-4"按相似度排序"要求一致。
- 技术栈一致：SQLite 原生扩展，无新依赖。

**具体实例**：
用户在素材提取清单查询"房建监理甲级"。FTS5 在素材库的 OCR 文本和命名关键字索引中匹配，返回"资质证书_房屋建筑工程甲级_20281222"（BM25 评分 0.95）、"房屋建筑工程甲级_20281222"（0.72）等结果，按相似度排序展示，用户多选确认。

### BP-9 三级素材管理与历史复用

| 字段 | 内容 |
|---|---|
| 优先级 | 低 |
| 适用阶段 | Phase 1.2 商务标（素材库管理） |
| 关联 spec | FR-4 素材库管理 |

**易标做法**：
知识库按"文件夹/文档/条目"三级管理，支持关键词检索和历史案例复用——历史项目的知识库条目可复用到新项目。

**借鉴理由**：
bidcraft 素材库（FR-4）已有层级分类（资质/人员/业绩/荣誉/财务/项目独享），企业级共享。可借鉴三级结构思路 + 历史标书的素材提取清单复用——新项目可参考历史项目的素材清单，减少循环收敛轮次。

**对 bidcraft 的增益**：
- 素材组织清晰：三级结构便于浏览和管理。
- 历史复用：新项目可导入历史项目的素材提取清单作为起点。
- 跨项目效率：企业级共享素材 + 历史清单复用，减少重复劳动。

**具体实例**：
企业级素材库按"资质/人员/业绩"一级分类 → "人员/张三"二级文件夹 → "注册证书_监理工程师_20281222"三级条目组织。新项目"和县柳庄路"创建素材提取清单时，系统提示"历史项目'XX道路工程'有相似清单，是否导入作为起点"，用户确认后导入，在其基础上修改，减少 2-3 轮循环收敛。

### BP-10 提示词缓存预热

| 字段 | 内容 |
|---|---|
| 优先级 | 低 |
| 适用阶段 | Phase 1.1 解析（LLM 可选路径） |
| 关联 spec | FR-2 第 3 点（可选路径 LLM）、EM-4 模型路由与成本可观测 |

**易标做法**：
为利用提示词缓存（Prompt Caching）降低成本：先单独运行"项目概述"项，成功后等待 5 秒（使缓存生效），再将其余解析项全部并发提交。系统提示 + 完整招标文件作为公共前缀被缓存，后续请求只付增量 token 费用。

**借鉴理由**：
bidcraft 解析阶段若开启 LLM（校验模式/双通道模式），多解析项调用 LLM 时共享相同的"系统提示 + 完整招标文件"前缀。借鉴缓存预热策略可降低 token 成本。EM-4 已要求"成本可观测"，此策略是成本优化手段。

**对 bidcraft 的增益**：
- LLM 调用成本降低：公共前缀（系统提示 + 招标文件全文）只计费一次，后续请求命中缓存。
- 并发效率：预热后其余项并发提交，总耗时接近单次调用。
- 成本可观测：EM-4 的 llm_call_log 可对比预热前后的 token 消耗。

**具体实例**：
解析阶段开启双通道模式，链路 2（LLM 独立抽取）需对 18 项各调用一次 LLM。系统先跑"项目概述"项（含系统提示 + 完整招标文件），成功后等待 5 秒使缓存生效，再将其余 17 项并发提交。每项的公共前缀（约 8000 token）命中缓存，只付增量 token（约 500 token/项），总成本降低约 60%。

1. **不复制代码**：所有借鉴点均以"按 bidcraft 自身架构重写"方式实现，AGPL-3.0 合规。

5. **测试覆盖**：借鉴点落地时须有对应测试（如 BP-3 Schema 校验需单测、BP-1 断点续跑需集成测、BP-2 警告清单需 E2E 验证）。
