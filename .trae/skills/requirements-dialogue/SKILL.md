# 需求对话协议（Requirements Dialogue Protocol）

## 目标

确保在进入编码前，AI 对用户需求的理解准确、无偏差、无遗漏，并将确认后的需求结构化沉淀到 spec.md / checklist.md / tasks.md。

## 硬约束（最高优先级）

- 在收到用户**明确的开始编码指令**（如"开始编码""开始写代码""动手写""实现 xxx"）之前，**不得编写任何代码**。
  - 禁止：新建源码文件、修改实现逻辑、运行构建/编译、安装依赖到项目。
  - 允许：读写文档、查询信息、设计方案、创建/更新 skill 与项目规则。
- 此约束高于任何其他默认行为。

## 对话流程（每个话题严格执行）

1. **倾听**：接收用户对某一话题的描述。一次只聊一个话题。
2. **复述**：用自己的话重述理解，提炼 2-5 个要点，主动暴露可能的理解偏差。
3. **追问**：针对范围边界、非目标、异常场景提 1-3 个澄清问题。若用户描述已足够清晰，可省略并直接进入确认。
4. **确认**：合并用户回复，给出最终理解，等待用户明确确认（如"确认""好的""对"）。**未确认不得落盘**。
5. **落盘**：将确认内容写入对应的 spec.md / checklist.md / tasks.md 字段。
6. **推进**：进入下一话题；若用户切换话题，则跟随用户。

## 落盘规则

- **spec.md**：需求类内容（项目简介、目的、目标用户、目标、非目标、功能需求、非功能需求、约束、假设、验收标准、待解决问题）。
- **checklist.md**：过程检查项（需求/规划/实施/验收/发布各阶段检查点）。
- **tasks.md**：仅在需求确认并完成规划后拆解任务；需求讨论阶段不得提前创建实现任务。
- 每次落盘后，向用户报告写入的具体位置和内容摘要。

## 迭代规则

- skill、项目规则、spec.md、checklist.md、tasks.md 均可迭代。
- 迭代必须基于用户明确指令或确认后的修改，不得自行扩展业务需求。
- 重大变更（如协议步骤调整、硬约束修改）需向用户说明并获得确认。

## 防偏差自检（每次落盘前）

- [ ] 我是否用自己的话复述了用户的需求？
- [ ] 是否已澄清范围边界和非目标？
- [ ] 用户是否已明确确认？
- [ ] 写入的内容是否仅来自用户确认的信息（无自行编造）？
